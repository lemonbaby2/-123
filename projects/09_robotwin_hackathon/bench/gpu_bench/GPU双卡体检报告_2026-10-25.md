## 一、结论先行（四句话）

1. **两张卡硬件都是健康的** —— 显存 82 项检查零错误，满载零降频，温度 63/73 °C 都很好。没有"坏孔"。
2. **功率能不能跑满**：5060 Ti 跑到 **152.9 W / 180 W = 84.9%** 满载率，是正常的
   （没顶到上限是因为我这轮加载的是纯 GEMM + 访存负载，真正跑 YOLO 训练会更高）；4060 在 Windows WDDM 下**不回报功耗读数**，这是驱动限制，不是卡的问题。
3. **能做分布式训练吗 —— 能，但不要做。** 两张卡之间 **P2P 不可用**，拷贝带宽实测只有 **5.3 GB/s**。数据并行的通信开销会超过计算收益，**跑出来的加速比大概率 < 1（比单卡还慢）**。
4. **模型部署是这两张卡的主战场** —— 5060 Ti 的 FP16 算力是 4060 的 **1.72 倍**，显存 **2 倍**。正确用法是**任务级并行**：一张跑训练/推理，一张同时干别的。

## 三、实测数据

### 3.1 算力（GEMM 4096³，20 次取平均）

| 精度 | RTX 4060 | RTX 5060 Ti | 倍率 |
|---|---|---|---|
| **FP32** | 7.12 TFLOPS | **16.31 TFLOPS** | **2.29×** |
| TF32 | 14.05 TFLOPS | 24.50 TFLOPS | 1.74× |
| **FP16（Tensor Core）** | 28.95 TFLOPS | **49.73 TFLOPS** | **1.72×** |
| BF16 | 29.64 TFLOPS | 48.88 TFLOPS | 1.65× |

**判读**：
- 5060 Ti 全面领先 **1.7~2.3 倍**，这张卡是毫无疑问的主力。
- **4060 的 FP32 只有理论值的 ~47%**，而 5060 Ti 达到 ~72%。
  原因不是硬件问题 —— **4060 挂着显示器**，`dwm.exe` 桌面合成持续占用 SM 和显存。
  这直接印证了后面的建议：**训练任务必须显式指定到 1 号卡**。

### 3.2 显存坏块检测（你问的"坏孔"）

每张卡 **41 项检查**，覆盖 75% 空闲显存：

| 检查项 | RTX 4060 | RTX 5060 Ti |
|---|---|---|
| Pattern 校验（8 种：全0/全1/0xAA/0x55/高低半字/首尾单bit） | ✅ | ✅ |
| **逐 bit 走位**（64 MiB × 32 轮，专抓 stuck bit） | ✅ | ✅ |
| 伪随机 Pattern（抓地址译码/相邻耦合串扰） | ✅ | ✅ |
| **错误总数** | **0** | **0** |
| 测试容量 | 5.20 GiB | 11.04 GiB |

```
[0] RTX 4060:     PASS  (41 项检查, 错误 0, 耗时 1.6s)
[1] RTX 5060 Ti:  PASS  (41 项检查, 错误 0, 耗时 1.8s)
```

⚠️ **为什么这项必须做**：GeForce 卡**没有 ECC**。数据中心卡的 ECC 会自动纠正并记录错误，
消费卡不会 —— 显存出错就是**静默脏数据**，训练时表现为 loss 突然变 NaN、推理时出现诡异伪影，
而且极难定位。这两张卡目前是干净的，可以放心用。**建议每个月重跑一次。**

### 3.4 烤机稳定性（双卡同时满载 150 秒）

关于功耗读数的说明：

## 四、互联拓扑 —— 分布式训练的致命伤

```
$ nvidia-smi topo -m
        GPU0    GPU1
GPU0     X      SYS
GPU1    SYS      X
```

`SYS` = 跨越 PCIe 且跨越 CPU 之间的 SMP 互连。翻译成人话：
**两张卡连在不同的 PCIe Root Complex 上，数据要 GPU 显存 → CPU 内存 → 另一张卡，两次穿越 PCIe。**

### 实测数据

```
P2P 访问矩阵:
  cuda:0 -> cuda:1 : ❌ 不可（需绕 CPU 内存）
  cuda:1 -> cuda:0 : ❌ 不可（需绕 CPU 内存）

GPU 间拷贝带宽:
  cuda:0 -> cuda:1   16~2048 MiB   →   4.76 ~ 5.46 GB/s
  cuda:1 -> cuda:0   16~2048 MiB   →   5.33 ~ 5.70 GB/s
```

**稳定的 5.0~5.7 GB/s，且与数据量大小无关。**

对比参照：

| 互联 | 带宽 | 这台机器 |
|---|---|---|
| NVLink 4（H100） | 900 GB/s | ❌ 没有 |
| PCIe Gen4 ×16 单根 | ~25 GB/s | ❌ 不是 |
| **本机（P2P 关闭，绕 CPU）** | **5.3 GB/s** | ✅ **就是它** |

注意 5060 Ti 只有 **Gen4 ×4**（理论单向 7.9 GB/s），实测 5.3 GB/s 已经是那条链路的 ~67%，
因为绕了 CPU 内存所以打了折扣。**这是硬件上限，改不了。**

### 算一笔账：为什么数据并行会变慢

以 ResNet-18（11M 参数，梯度约 44 MB）为例：

| 项目 | 数值 |
|---|---|
| 一次 allReduce 的有效传输量 | ≈ 88 MB（2× 梯度，绕行导致） |
| 通信耗时 @ 5.3 GB/s | **≈ 16.6 ms** |
| 单卡 batch=32 训练步耗时（估算） | ≈ 20~25 ms |
| **通信 / 计算比** | **66%~83%** |

这意味着**每一步有一半以上时间在等通信**。再加上：

- **算力不对等**（7.1 vs 16.3 FP32 TFLOPS）→ 快的卡要等慢的，**木桶效应**
- **显存不对等**（8 vs 16 GB）→ batch size 无法对称切分
- **4060 还挂着桌面** → 额外被抢 SM

实际加速比大概率 **0.7~1.2×**，也就是**跑双卡还不如单独跑 5060 Ti。**

### 软件栈还补了一刀

**Windows 原生 PyTorch 不支持 NCCL。** `torch.distributed` 的 NCCL 后端只在 Linux 提供，
Windows 上只有 `gloo`，而 **gloo 不支持 GPU 间的直接集合通信**（必须绕 CPU）。

所以这条路上今天连门都没开。期间我试过 WSL2 路线，但 WSL 的 Ubuntu-22.04
在装 CUDA 版 torch 时**整个实例崩了**（`Wsl/Service/CreateInstance/ERROR_NETNAME_DELETED`），
目前处于 Stopped 状态 —— 稳定性也存疑。

## 五、那这两张卡该怎么用

### ✅ 强烈推荐：任务级并行

两张卡各干各的，零通信 —— **这才是这种配置的最优解**：

```
GPU1（RTX 5060 Ti / 16 GB）── 主力：YOLO 训练、VLA 微调、大模型推理
GPU0（RTX 4060 / 8 GB）  ── 副手：NVENC 转码、数据预处理、
                               Grounding DINO 预标注、桌面输出
```

对你的 E281 产线流水线，这个组合是**天然适配**的：

| 任务 | 放哪张卡 | 理由 |
|---|---|---|
| YOLOv8/YOLO11 训练（imgsz 960） | **5060 Ti** | 16 GB 能吃更大 batch；FP16 算力 1.7 倍 |
| VLA 微调（SmolVLA / π0 级别） | **5060 Ti** | 显存优先 |
| **NVENC 视频转码（产线素材）** | **任意 / 可双开** | **不占 SM**，NVENC 是独立单元 |
| Grounding DINO / DWARF 预标注 | 4060 | 后台跑，不占主力 |
| RKNN / Hailo 导出前的 ONNX 校验 | 4060 | CPU+GPU 混合，不影响训练 |
| 日常桌面显示 | 4060 | 保持现状 |
| Qwen2.5-VL-3B / 7B 量化推理 | 5060 Ti | 7B Q4 可跑 |

### ✅ 完全可行：模型部署 / 推理

单卡推理没有任何通信开销，这是两张卡最擅长的：

| 场景 | 5060 Ti (16 GB) | 4060 (8 GB) |
|---|---|---|
| YOLOv8s/m FP16/INT8 实时推理 | ✅ 绰绰有余 | ✅ 足够 |
| 多路视频并发推理 | ✅ 4~8 路 | 🟡 2~4 路 |
| Qwen2.5-VL-3B / 7B 量化 | ✅ 7B Q4 可跑 | 🟡 3B 级别 |
| Grounding DINO 零样本预标注 | ✅ | ✅ |
| TensorRT / RKNN 导出部署 | ✅ | ✅ |

**部署一定要走 TensorRT / RKNN 导出**，别用 PyTorch 原生推理。
5060 Ti 是第 5 代 Tensor Core，对 FP8/INT8 有原生支持，量化收益明显。

### 🟡 审慎：模型并行（Model Parallel）

如果模型一张卡塞不下（想本地跑 14B~32B 的多模态模型），**切分层**比数据并行合理得多：

```
输入 → [GPU1: 层 0~N/2] → [GPU0: 层 N/2~N] → 输出
```

优点：通信量只有**层间激活值**（远小于全量梯度），且可以用 micro-batch 流水线填满。
缺点：需要手写切分逻辑，生态没数据并行成熟。

16 + 8 = **24 GB 总显存**，理论上能塞下 **30B 级别的 Q4 量化模型**（权重约 16 GB）。
这条路是走得通的，比数据并行靠谱得多。

## 六、立即可操作

### 今天就做

1. **训练显式指定到 1 号卡**（这条最重要，否则 PyTorch 会默认抓 0 号卡然后 OOM）：
   ```bash
   # Linux / WSL
   CUDA_VISIBLE_DEVICES=1 python train.py

   # YOLO 写法
   yolo train model=yolov8s.pt device=1 imgsz=960 batch=16
   ```

2. **编译自定义算子必须写全两个架构**，否则 5060 Ti 上直接报错
   `no kernel image is available for execution`：
   ```bash
   # Windows
   set TORCH_CUDA_ARCH_LIST=8.9 12.0
   # Linux / WSL
   export TORCH_CUDA_ARCH_LIST="8.9 12.0"
   ```
   ⚠️ 另外：**WSL 里现装的 CUDA Toolkit 是 12.6，编译不出 `sm_120` 的代码**。
   必须升级到 12.8+，否则 5060 Ti 在这个环境里跑不了自定义算子。

3. **监控 5060 Ti 的散热**。它空载 65 °C 就比 4060 高 20 °C，
   虽然满载 73 °C 没问题，但夏天要留意。

### 值得做

4. 检查 5060 Ti 的 **12VHPWR 供电线是否插到底**（180 W 的卡接触不良是高发问题，
   表现为满载时频率剧烈震荡 —— 目前 1.6% 降频说明是好的，但值得确认）。
5. 真的要做分布式训练的话，**单独搞一台 Linux 机器**，或买同型号双卡 + 支持 NVLink 的平台。
   **这台机器不是干这个的，别在这上面耗时间。**
6. WSL2 实例目前处于 Stopped 状态（装包时崩过），需要的话我可以帮你重建。
